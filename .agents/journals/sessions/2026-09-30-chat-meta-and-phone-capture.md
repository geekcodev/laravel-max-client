# Метаданные чата и телефон из контакта: исследование и план

## Проблема

Интегратор (i2tech) указал два пробела реестров.

1. Для групп и каналов в `max_chats` нет названия — видно только имя пользователя, добавившего бота, и его
   `user_id`. Операторский чат Filament показывает именно это.
2. Телефон из вложения-контакта (`request_contact`) не попадает в `max_users.phone`, хотя колонка есть. В i2tech
   реализовано вручную: разбор vCard, проверка HMAC, запись в реестр.

## Исследование

- `max_chats` вообще не имеет колонки под название
  (`database/migrations/0001_01_01_000002_create_max_chats_table.php:12`).
- Апдейты `bot_added`/`bot_started` название не несут: в спеке `title` есть только у `chat_title_changed`. Единственный
  источник — `GET /chats/{chat_id}`.
- `PersistMaxChatListener::resolveChatTypeViaApi()` (`src/Listeners/PersistMaxChatListener.php:162-176`)
  этот запрос уже делает, но берёт только `->type`.
- Хуже: вызов разрешён только при `chat_type === null` **и** `is_channel === null` (`:86-88`). Для группы и канала
  `is_channel: true`, то есть название не запрашивается именно там, где оно нужно.
- `chat_title_changed` не обрабатывается вовсе, хотя `Update::$title` ядром уже разобран.
- Логика `getChat()` с кэшем и дозаписью `chat_type` продублирована в
  `src/Services/MaxUserProfileService.php:195-235`.
- `last_activity_at` не обновляется на `message_created` и комментариях: ранний `return` на `:37-41`.
- Индекса по `chat_id` нет, а уникальный индекс на `[user_id, chat_id]` запрос `where('chat_id', ?)`
  не покрывает. В PostgreSQL это последовательное сканирование на каждое входящее сообщение.
- По телефону: у входящего `ContactAttachmentPayload` в спеке нет `vcf_phone` — только `vcf_info`, `max_info`,
  `hash`. `vcf_phone` есть лишь в исходящем `ContactAttachmentRequestPayload`. Значит `vcfPhone` на входе всегда
  `null`, и разбор vCard из i2tech — не запасной путь, а единственный рабочий. Это пробел ядра.
- `ContactVerifier` ядра HMAC-проверку уже делает (CRLF, hex и base64, `hash_equals`) — дублировать нельзя.
- `max_users.phone` есть, отметки времени получения нет. Записи в `max_users` идут из трёх мест, все пишут явным списком
  полей, `phone` не затрагивается.
- Миграции публикуются тегом `laravel-max-client-migrations` (`src/MaxServiceProvider.php:138-144`), но автоподгрузки
  нет: без `vendor:publish` миграций в приложении не существует.
- Проверено по коду Laravel, чем грозит сочетание публикации и автоподгрузки:
  `Migrator::getMigrationFiles()` применяет `keyBy(getMigrationName($file))`, поэтому дубли одного имени выполняются
  один раз, но оставляется **последнее** вхождение, а `BaseCommand.php:29` собирает пути как
  `array_merge($migrator->paths(), [$this->getMigrationPath()])` — путь приложения идёт последним. Значит опубликованная
  копия перекрывает файл пакета, и исправление в пакете до такого потребителя не доходит.

## Решение

План `.agents/plans/2026-09-30-chat-meta-and-phone-capture.md`, три независимых блока.

Блок A — метаданные чата: дополнение существующей миграции `create_max_chats_table` полями `title`,
`description`, `link`, `icon_url`, `title_checked_at` и индексом по `chat_id`; новый `MaxChatProfileService`
(один `getChat` на все записи реестра чата); `PersistMaxChatListener` пишет ответ целиком и обрабатывает
`chat_title_changed` без запроса к API; аксессор `MaxChat::displayName()`; флаги `chats.fetch_metadata`
и `chats.title_check_interval`; команда `max:chats:refresh`; `filament-max-chat` переключается на `displayName()`.

Блок B — телефон: в ядро `ContactPhoneExtractor::fromVcf()`; дополнение существующей миграции
`create_max_users_table` полем `phone_verified_at`; `MaxContactService` (проверка подписи плюс извлечение номера)
и `PersistMaxUserPhoneListener` под флагом `users.capture_phone` (по умолчанию выключено — персональные данные); в
i2tech дублирующий код удаляется. Источник номера один — разбор `vcf_info`, поле `vcf_phone` на входе не приходит.

Блок C — схема и миграции. По решению владельца репозитория новая миграция не создаётся, существующие
`create_max_users_table` и `create_max_chats_table` дополняются на месте, имена файлов не меняются. В
`MaxServiceProvider::boot()` добавляется `loadMigrationsFrom()` вне `runningInConsole()`, тег публикации миграций
снимается, в README описывается порядок обновления с удалением ранее опубликованных копий.

## Нюансы

- Изменение уже выполненной миграции не обновляет существующие базы: имя миграции есть в таблице `migrations`,
  `create` повторно не выполнится. Для обновления существующих установок вводится идемпотентная команда
  `php artisan max:upgrade` с проверками существования колонки и индекса. Без неё первый же `message_created`
  у обновлённого потребителя упадёт с «Unknown column» — это главный риск задачи.
- `Schema::hasIndex()` в Laravel нет, проверка индекса идёт запросом к списку индексов схемы; имя индекса фиксируется,
  иначе повторный запуск добавит дубликат.
- Пустой `title` в ответе не должен затирать уже известное название.
- Телефон и `vcf_info` не логируются (A09); в лог только идентификаторы и факт действия.
- Значение `TEL` в vCard ядро не валидирует и не нормализует: нормализация номера — ответственность потребителя, иначе
  пакет начнёт отбрасывать валидные значения.
- Отличающийся телефон перезаписывается: контакт формируется платформой из номера аккаунта отправителя, значит это смена
  номера, а не чужой контакт.
- В группе на 50 участников должен быть один запрос `getChat`, а не пятьдесят.
- Релизы: адаптер `v1.1.4` (PATCH, предыдущий тег `v1.1.3`), ядро `v1.1.8`.
