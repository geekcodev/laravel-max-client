# Метаданные чата, телефон из контакта, обновление схемы и ядро v1.1.8

## Проблема

Три независимые задачи, найденные в интеграционном проекте i2tech и в свежем релизе ядра.

1. В `max_chats` нет названия группы и канала: колонки не было, `getChat()` отбрасывал `title`, а условие вызова
   исключало `is_channel: true`.
2. Апдейт `request_contact` несёт подтверждённый телефон, но в `max_users` он не попадал.
3. Уже установленная версия пакета не получала новые колонки: миграции пакета публиковались, а изменённый файл уже
   отмечен выполненным.

## Решение

### Метаданные чата

`Services\MaxChatProfileService` (singleton) — единственный источник метаданных. Название, описание, ссылка и иконка
приходят только из `getChat()`; апдейты `bot_added`/`bot_started` несут лишь `chat_id`/`user`/
`is_channel`, а название приходит отдельным `chat_title_changed`.

- Один ответ пишется во все записи реестра с этим `chat_id`: в группе по записи на каждого участника, поэтому на 50
  участников приходится один запрос, а не пятьдесят.
- Пустой ответ не затирает известное значение (публичный канал без названия — обычное дело).
- `chat_type` дозаполняется только при `null`.
- Кэш ответа живёт на время работы; `forgetChatCache()` сбрасывает.
- `PersistMaxChatListener` пишет `title` из `chat_title_changed` во все записи чата, без запроса к API.
- `message_created`/`message_callback` и комментарии обновляют `last_activity_at` — раньше ранний `return`
  оставлял его старым, и сортировка чатов по свежести врала.
- `MaxUserProfileService` переведён на делегирование в `MaxChatProfileService`, дублирование `chatTypeFor()`
  и кэша снято.

API: `sync(int): bool`, `refresh(int|list<int>|null): bool`, `pendingChatIds(...)`, `chatTypeFor(int)`,
`activeChatIds()`. Команда `max:chats:refresh [--all|--chat=ID]` печатает, сколько чатов к проверке и сколько пропущено
как проверенные недавно — иначе из расписания не видно, был ли запрос вообще.

### Телефон из контакта

`Services\MaxContactService` + `Listeners\PersistMaxUserPhoneListener`. Порядок извлечения номера — рекомендованный
ядром: `vcfPhone ?? ContactPhoneExtractor::fromVcf($vcfInfo)`. Обрабатываются только
`message_created`/`message_callback`; `comment_*` и `bot_*` игнорируются. Проверка подписи и разбор vCard — только ядром
(`ContactVerifier`, `ContactPhoneExtractor`), дублирования нет.

Телефон и `vcf_info` не логируются (A09). Известный отличающийся номер не перетирается: расхождение пишется в лог без
значений. Тот же номер обновляет только `phone_verified_at` — отметка всегда описывает текущее сохранённое значение.
Выключено по умолчанию: `MAX_USERS_CAPTURE_PHONE=false` (персональные данные).

### Схема и миграции

Первая версия решения (дополнить `create_max_users_table` и `create_max_chats_table` на месте) была ошибочной, и
владелец её отменил: у уже установленных проектов файлы создания таблиц числятся выполненными, поэтому
`php artisan migrate` отработал бы вхолостую и схема молча осталась бы прежней.

Итог: новые поля и индекс вынесены в отдельные аддитивные миграции, имена продолжают последовательность
`0001_01_01_`: `0001_01_01_000003_add_phone_verified_at_to_max_users_table.php`,
`0001_01_01_000004_add_chat_id_index_to_max_chats_table.php`,
`0001_01_01_000005_add_chat_metadata_to_max_chats_table.php`; файлы создания таблиц заморожены. Индекс по
`chat_id` вынесен в отдельный файл и поставлен раньше колонок: он нужен сам по себе и на большой таблице строится, пока
таблица ещё не получила новые колонки. Обновление пакета сводится к `composer update` плюс
`php artisan migrate` без ручного вмешательства.

В `MaxServiceProvider::boot()` добавлен `loadMigrationsFrom()`, тег публикации миграций снят: опубликованная копия
приложения перекрывает файл пакета, то есть опубликованные миграции переставали бы обновляться.
`max:upgrade [--dry-run]` сохранён как страховка для рассинхронизации (ручные правки схемы, ранее опубликованные
миграции), а не как обязательный шаг обновления.

### Зависимости

Constraint ядра `^1.1.6` → `^1.1.8` (v1.1.7 добавил `ContactPhoneExtractor`, v1.1.8 — документация).

## Тесты

`MaxMigrationsUpgradeTest` моделирует установку прежней версии: создаёт старую схему и помечает файлы создания таблиц
выполненными, после чего обычный `php artisan migrate` обязан добавить колонки, сохранить данные и не переиграть
создание таблиц. Guard-тесты фиксируют решение: `testCreateMigrationsStayFrozen`,
`testNewColumnsAreDeclaredInAdditiveMigrationsOnly` и `testChatIdIndexHasItsOwnMigration` падают, если вернуть правку на
место или вернуть индекс в миграцию с колонками. Все три падения проверены вручную.

`MaxUpgradeCommandTest` покрывает страховку: два запуска подряд, второй не добавляет дубль индекса и не меняет состав
колонок. В тестах телефона — проверка, что номер, `vcf_info` и хеш не попадают в лог (A09).

## Решение: флаг MAX_USERS_CAPTURE_PHONE убран

Первая версия включала запись телефона только при `users.capture_phone` (default false) и не перетирала отличающийся
номер. Оба решения пересмотрены после чтения документации ядра: контакт приходит только через кнопку `request_contact` и
формируется платформой из номера аккаунта отправителя (регистрация в MAX возможна на один номер), поэтому это
гарантированно номер самого пользователя, а пересланный контакт приходит файлом и в этот путь не попадает. Флаг не
защищал ни от чего и только создавал ложное ощущение контроля; правило «не перетирать» при смене номера аккаунта
оставляло бы пользователя навсегда при старом значении.

Теперь: флага нет, запись всегда, отличающийся номер перезаписывается, факт смены логируется без значений. Побочный
эффект: слушатель телефона теперь регистрируется всегда, поэтому проверки «нет слушателей — не ставить задачу» в трёх
тестах (вебхук-контроллер, джоб, max:listen) перестали проходить на прежнем предусловии. Код не менялся — предусловие в
тестах задаётся явно через `Event::forget()`.

## Найденный баг: новая запись участника оставалась без метаданных

Разбор сценария «канал/группа, название не задано» вскрыл расхождение: проверка перед запросом
`hasKnownTitle()` использовала `exists()` (есть ли хоть одна заполненная строка), а заполнение в `sync()`
идёт по всем строкам с `chat_id`. Проверка и заполнение мерили разные вещи.

Сценарий: участник 111 нажал «старт» → запись создана, `title` пуст → запроса ещё не было → `getChat` → заполнены все
строки. Участник 222 нажал «старт» позже → его запись создана пустой → проверка увидела заполненную строку участника 111
и пропустила запрос → метаданных у него нет. Итог: реестр частично заполнен, название есть у одного участника группы и
отсутствует у остальных. Путь не экзотический — записи создаются по мере прихода участников, поэтому все участники после
первого оставались пустыми.

Наивная замена на «заполнены ли все» не подходит: новая запись всегда только что создана и всегда пуста, поэтому каждый
участник дал бы по одному одинаковому `getChat` — ровно та стоимость, ради которой один ответ пишется во все записи.

Исправление: `MaxChatProfileService::ensureMetadata()` с правилом в три состояния на `chat_id` — неизвестно нигде →
`getChat` и запись всем; часть пуста → `inheritKnownMetadata()` копирует известное из заполненной строки без запроса;
заполнены все → ничего. Существующие значения не затираются, `title_checked_at`
переносится вместе с данными, чтобы периодичность проверки считалась одинаково. Правило переехало в сервис, слушатель
вызывает `ensureMetadata()` и больше не содержит `hasKnownTitle()`.

Тесты: `testSecondMemberOfSameChatInheritsMetadataWithoutSecondRequest` (уровень слушателя, сначала падал на 4-м
утверждении), четыре теста на `ensureMetadata`/`inheritKnownMetadata` в сервисе, включая регрессию на исходный баг и
запрет затирать уже известное значение.

## Найденный баг: bot_removed без user терялся, чат навсегда оставался active

Разбор схемы `max_chats` показал, что `user_id` в ней не оправдан: все прочие колонки — свойства чата. Поиск по коду:
`user_id` читается ровно в одном месте, `MaxUser::chats()`. Реструктуризация в одну строку на чат плюс отдельная
`max_chat_users` зафиксирована в плане как отложенная на отдельный релиз.

Но следствие текущей схемы воспроизводится и чинится точечно: слушатель пропускал апдейт без
`user_id`, а `bot_removed`/`bot_stopped` идут без message и колбэка, значит `user` в них null. Слушатель терял удаление
бота, чат оставался `status = active` навсегда, `activeChatIds()` продолжал его возвращать, и `max:chats:refresh`
опрашивал `getChat` бесконечно.

Проверено пробным тестом до правки: `bot_started` с пользователем → `active`; `bot_removed` без пользователя → статус не
меняется. Пробный файл удалён.

Правка: `bot_*` — события о боте в чате, а не о пользователе, поэтому при `userId === null` новая строка не заводится
(`user_id` часть уникального ключа), но `status`, `last_activity_at` и `chat_type`
обновляются во всех записях с этим `chat_id` — `applyStatusToKnownRows()`. Схему не трогаем, миграций не требуется.
Записей нет — ничего не меняется. Это общий путь для всех четырёх событий, включая
`bot_added` без user, который реактивирует записи чата.

Восемь тестов в `PersistMaxChatListenerTest`: removed и stopped без user пишут статус во все строки,
`bot_added` без user реактивирует, `last_activity_at` обновляется, для неизвестного чата строки не создаются, без
`chat_id` ничего не меняется, чужие чаты не затрагиваются, `chat_type` дозаполняется.

## Релиз: v1.1.4, а не 1.2.0

Пользователь уточнил, что релиз — patch `v1.1.4` (предыдущий тег `v1.1.3`), а не `v1.2.0`. Это меняет планку по BC: в
patch нельзя ни удалять, ни менять публичные сигнатуры.

Сверка публичного API с тегом `v1.1.3` скриптом: удалённых методов 0 (значит, удаление
`Config::usersCapturePhone()` не ломающее — метода не было ни в одном теге), добавлено 23, изменены сигнатуры двух
конструкторов: `PersistMaxChatListener` (`Config, ApiClient` → `Config,
MaxChatProfileService`) и `MaxUserProfileService` (добавлен четвёртый параметр).

Варианты были два: сохранить старые сигнатуры мёртвым параметром либо оставить чистые и задокументировать исключение.
Выбрано второе по решению пользователя — держать неиспользуемый `ApiClient` в слушателе ради совместимости неоправданно.
Оба класса помечены в docblock как внутренние, в release notes добавлен раздел «Изменение (BC)» с таблицей старых и
новых сигнатур.

Попутно выяснилось, что в планах и журналах версия ядра была указана как `v1.2.0`, хотя фактически ядро на `v1.1.8` и
constraint в `composer.json` — `^1.1.8`. Исправлено. Заодно в AGENTS.md последний выпущенный релиз адаптера обновлён с
`v1.1.2` на `v1.1.3` по фактическому тегу.

## Аудит полноты плана

План `.agents/plans/2026-09-30-chat-meta-and-phone-capture.md` сверен с кодом по пунктам, а не по памяти. Остались три
расхождения, все исправлены:

1. **Пункт C.3 не был выполнен.** README не содержал инструкции удалить ранее опубликованные копии миграций, хотя план
   называет это главным источником ошибок при обновлении. Причина неочевидна:
   `Migrator::getMigrationFiles()` собирает файлы через `keyBy()` по имени миграции, пути пакета идут раньше пути
   приложения, поэтому последнее вхождение имени — файл из `database/migrations`
   потребителя. Копия молча перекрывает файл пакета, и правка пакета до потребителя не доходит. Добавлен раздел «Если
   миграции пакета публиковались раньше» с проверкой, командами удаления и пояснением, что строки в таблице `migrations`
   удалять не нужно.
2. **Строка «Публичные сигнатуры не меняются» в плане стала ложной** после решения по BC. Заменена на фактическое
   состояние: 0 удалённых, 23 добавленных, 2 изменённых конструктора.
3. **`MaxServiceProvider` описан неточно** в release notes: формулировка утверждала, что привязка приложена в
   `register()` для обоих классов. Фактически `MaxUserProfileService` биндится в
   `register()` (`:94`), а `PersistMaxChatListener` в привязке не участвует вовсе — он регистрируется как класс
   слушателя в `boot()` (`:197`).

Отдельно: строка `v1.1.4` в таблице «История изменений» README была вставлена четырьмя физическими строками, причём три
из них не начиналися с `|`, — таблица Markdown там разваливалась. Склеена в одну строку и проверена структурно (у всех
строк ровно 4 разделителя). Первая попытка склейки потеряла начало ячейки («Метаданные чатов … одним запросом»), строка
восстановлена по исходному тексту.

Пункты A.8 (`filament-max-chat`) и B.7 (доработка `i2tech`) отмечены в плане как вне периметра: это другие репозитории,
здесь они не верифицируются.

## Нюансы

- `Artisan::output()` переиспользует и очищает общий `BufferedOutput`: при нескольких вызовах подряд вывод надо забирать
  сразу в переменную, иначе второе чтение вернёт пустую строку.
- `$this->components->info()` не попадает в `expectsOutputToContain` — только в `Artisan::output()`.
- `phone_verified_at` описывает текущее сохранённое значение, поэтому идентичное повторное подтверждение двигает отметку
  вперёд, а расхождение сохраняет старую отметку вместе со старым номером.
- `MaxChatsRefreshCommand` не делает `is_channel: true` пропуском: `is_channel` в апдейте не отражает тип канала, а
  `chat_title_changed` приходит для диалогов и проверяется на непустоту `title`.
- `chat_id` в таблице bigint, а `pluck()` на некоторых драйверах отдаёт строки — идентификаторы нормализуются через
  `filter_var(..., FILTER_VALIDATE_INT)`.
- Docker-сеть без `--network host` не достаёт до Packagist; обновление зависимостей выполнялось с ретраями (curl error
  28).
